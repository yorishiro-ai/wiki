Before stopping use, [export the information you need](/wiki/guides/import-export/) and arrange a [backup](/wiki/operations/queue-publisher-cutover/) with the server operator. Disabling a tenant does not erase its data. Ask the operator separately if you need permanent deletion.

## Inspect before disabling

As the tenant root user, or a user allowed to read and update the tenant with a tenant-scoped key, ask your connected assistant:

> I want to stop using this tenant. Check retained data, unfinished work, and effects on schema copies in other workspaces. Do not disable anything yet.

Use `tenant_retirement_inventory` to review retained records, unfinished work, shared user accounts, and external schema forks. The REST endpoint is `GET /api/tenants/current/retirement`. The inventory reflects the time of the check; it does not authorize a later action. External forks may need attention before permanent deletion.

## Disable and retain data

Disabling needs tenant update permission and a tenant-scoped key. Check the name and UUID with `whoami`, save what you need, then request `disable_tenant`. Supply the target tenant UUID as `confirmed_tenant_id`. With the API, send the same value to `POST /api/tenants/current/disable`.

Disablement revokes every tenant key, including the one used for the request, so clients lose access. Pending work is cancelled, but data and occupied capacity remain. This is not a way to free space under a plan quota or manual cap.

Already-authenticated requests may finish. Not every external call already in progress can be stopped.

## Operator-only permanent cleanup

Permanent deletion cannot be undone. Save what you need and give the server operator the target UUID. Ordinary REST/MCP keys cannot perform it. Normal workspace deletion also protects the last workspace.

The operator selects the intended installation's configuration and uses the operator CLI. Keep production UUIDs and secrets out of shared examples.

| Task                        | Values and checks                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `inspect_tenant_retirement` | Use `tenant_id` to inspect retained data and consequences                                       |
| `disable_tenant`            | Match `confirmed_tenant_id` to `tenant_id`; data is retained                                    |
| `delete_tenant`             | Disable first, then match `confirmed_tenant_id` to `tenant_id`; permanently deletes tenant data |

Actual cleanup releases the occupied tenant capacity. It removes API-key history too, but preserves shared user accounts and secret-free retirement records.

## Delete an account

Leaving a tenant and deleting an account are different. Removing membership revokes the person's attributed tenant keys; a tenant user's account is deleted with its membership. Tenant administrators cannot delete the root user's account, which may belong to other tenants.

Ask the server operator to delete a root account. The operator checks the target with `list_users`, then uses `delete_user` with the same UUID in `user_id` and `confirmed_user_id`. Deleting the root account of an active tenant schedules that tenant for deletion after seven days, and the scheduler's `delete_due_tenants` task then deletes it. If the tenant is already disabled, it is deleted immediately. Root accounts that belong to no other tenant are retained when their tenant is deleted.

## Check limits

Retained usage after disablement, plan quotas, and manual caps are separate. If you only need to change a limit, see [Enterprise configuration](/wiki/configuration/enterprise/#plan-policy-and-job-limits) rather than retiring the tenant.
