Yorishiro records the life of every background job it submits: when it was queued, when a worker started it, and how it ended. You can use this to see whether jobs start as fast as you expect.

## How timing is measured

- **Queued time** is when the server saves the job. The time before the job is published to the queue counts toward the queue start time.
- **Start time** is when a worker first receives the job.
- **Queue start time** is start time minus queued time.

A retry or redelivery keeps the original queued time. The queue start time therefore includes the time a job spent waiting for another attempt.

## Job status

A job is `queued`, `running`, `retrying`, `completed`, `failed`, `cancelled`, or `unavailable`. Missing queue capacity and provider failures do not count as successful starts. A job becomes `unavailable` only when Yorishiro refuses it before it reaches the queue, for example when its worker target, concurrency policy, or starvation policy cannot be determined. Queue and provider failures do not set this status. When publishing fails, Yorishiro logs `dispatch outbox: enqueue failed and will be retried`, and the job stays `queued` or `retrying`. Publishing is asynchronous, so the request that submitted the job does not receive the provider error.

If the worker running a job stops responding for five minutes, the job counts as expired. The next delivery then starts a new attempt, and the earlier worker can no longer complete or retry the job.

Job records are stored in the application database, even though the queue runs in Valkey. When you diagnose a job, check both the queue and the job record.

## Monitor start times

When a job starts, Yorishiro logs the message `queue job admitted` with the field `queue_start_seconds`, which holds the job's queue start time in seconds. Filter for these events in your logging system to chart start times.

Terminal failures log `terminal worker failure`. With Enterprise plan policy on, a job held back because its target is at its limit logs `queue capacity saturated`, along with the current active capacity and the capacity limit for that target. The worker then logs `worker capacity saturated`.

If more and more jobs stay `queued`, `retrying`, or `unavailable`, check worker capacity and queue health before you judge start times.

## Objectives by plan

Enterprise plans define these objectives for how long a job should wait before it starts:

| Plan | Objective   |
| ---- | ----------- |
| Free | Best effort |
| Pro  | 60 seconds  |
| Team | 15 seconds  |

Yorishiro records the timings but does not enforce the objectives. Compare your recorded start times with them. Automatic Official bursts and compute charging are not available.

## Capacity

Run workers for the targets you need to reserve capacity for. See [Workers and queues](../../configuration/workers-and-queues/). A worker that serves several targets shares its slots across them and reserves none.

When a target reaches its limit, the job waits and tries again at its original priority and target. It does not move to another target. The Enterprise limits are described in [Enterprise configuration](../../configuration/enterprise/#plan-policy-and-job-limits).
