To move information to another workspace, export it to a file and import that file at the destination. Export includes the formats, saved items, and connections (schemas, entities, and relations) in the workspace your key accesses. It does not back up users, API keys, server settings, or the whole installation. See [Update and back up](../../operations/queue-publisher-cutover/) for a full backup.

## Export workspace content

Use a key with `read` scope. Replace the URL and key:

```sh
curl --fail-with-body http://localhost:5150/api/export.jsonl \
  -H 'Authorization: Bearer <api-key>' \
  -o workspace.jsonl
```

Check that the command succeeded before using the file. Keep the export private: it contains workspace content in plain text.

You can also ask your assistant:

> Export the connected workspace with `export_jsonl`. Check that it succeeded before giving me the JSON Lines content to save.

This requires `read` access. Keep the returned JSON Lines content unchanged for import; it contains one record per line, not one JSON value for the whole file.

Both REST and MCP exports are limited to 8 MiB and 10,000 total records, including schemas and relations. Exceeding either limit returns REST `422` or an MCP tool error, without a partial document. If your workspace exceeds these limits, ask the server operator to help plan the move. Paginated lists can help inspect the content, but they are not an import-ready export: schema lists omit full definitions, and moving relations also requires preserving connections between the destination items.

The file contains schemas in name/version order, followed by entities and then relations. Changes made during export can leave the content inconsistent; the file does not capture one fixed point in time. For a consistent backup of your installation, ask the server operator to follow [Update and back up](../../operations/queue-publisher-cutover/).

## Import into a workspace

Use the destination workspace's key with `schema` scope. Test in an empty workspace first; do not repeatedly import the same file into a working workspace.

```sh
curl --fail-with-body -X POST http://localhost:5150/api/import.jsonl \
  -H 'Authorization: Bearer <destination-api-key>' \
  -H 'Content-Type: application/x-ndjson' \
  --data-binary @workspace.jsonl
```

The response contains a `job_id`. This means the request was accepted, not that import has finished. Keep the application-job worker running and poll:

```sh
curl --fail-with-body http://localhost:5150/api/import-jobs/<job-id> \
  -H 'Authorization: Bearer <destination-api-key>'
```

Wait for `completed`. If it reports `failed`, inspect the error and logs before retrying. The worker imports the records together; a record error rolls the import back.

## Import through your assistant

Ask your connected assistant:

> Import this JSON Lines content. Check the destination workspace before starting, then check whether the import finishes.

The assistant submits the content with `import_jsonl` and checks `import_job_status` using the returned ID. Both require `schema` access. Check the export's size against your client's limits before sending its full contents through chat.

After import, search data may need rebuilding. Ask the administrator to run [resync_embeddings](../../configuration/embedding/#change-the-embedding-model) for the destination workspace if embeddings are missing. Verify imported items with a list or exact-ID read as well as a search.
