A tenant is the account area for a person or organization. Workspaces separate the information stored within it. Each tenant has one root user, and every other person is a tenant user whose permissions come from IAM policies. Ask the root user or an administrator to make the changes on this page.

## Sign in

| Who                | How                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------ |
| New tenant root    | `POST /auth/signup` with `email`, `password`, and optional `display_name`            |
| Existing root user | `POST /auth/root/login` with `email` and `password`                                  |
| Tenant user        | `POST /auth/tenant/login` with the `x-tenant-id` header, `user_name`, and `password` |

Signing up creates the tenant and its root user without a key. Sign-in returns a tenant-scoped API key only if the account belongs to exactly one active tenant. Save the key when it is shown; for workspace operations, send `X-Workspace-Id` as described in [API keys](/wiki/guides/api-keys/). A root account is retained when its tenant is deleted, but cannot sign in without a tenant membership.

## Add and remove people

> Create a tenant user named `alice` and show me the permissions before attaching a policy.

Use `create_tenant_user` with `user_name` (1 to 64 letters, digits, `.`, `_`, or `-`), a password of at least 12 characters, and an optional `display_name`. A new user has no permissions until you attach a policy or add the user to a group. Use `list_members` to see members and `reset_tenant_user_password` to replace a password; this revokes all of that person's keys. Root recovery is an operator task.

Before removing someone, use `preview_member_removal`. `remove_member` revokes the person's attributed keys and deletes a tenant user's account with the membership. The root user cannot be removed.

## Choose permissions with IAM

Permissions are IAM policies, evaluated per operation. The root user holds every permission. Other users get permissions from policies attached directly to them or to their groups.

The tenant starts with three policies:

| Policy               | Allows                                                             |
| -------------------- | ------------------------------------------------------------------ |
| Tenant Administrator | Every action                                                       |
| Tenant Writer        | Everything except tenant, user, credential, and IAM administration |
| Tenant Reader        | Read-only actions                                                  |

> Create a group named `readers`, attach the Tenant Reader policy, and add alice. Show each step first.

| Task                       | Tools                                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Policies                   | `create_iam_policy`, `get_iam_policy`, `list_iam_policies`, `update_iam_policy`, `delete_iam_policy`                                         |
| Groups                     | `create_iam_group`, `get_iam_group`, `list_iam_groups`, `update_iam_group`, `delete_iam_group`                                               |
| Group members and policies | `add_group_member`, `remove_group_member`, `list_iam_group_members`, `attach_group_policy`, `detach_group_policy`, `list_iam_group_policies` |
| User policies              | `attach_user_policy`, `detach_user_policy`, `list_iam_user_policies`                                                                         |
| Audit trail                | `list_iam_audit` (needs the independent `audit` grant)                                                                                       |

A policy document lists statements with an `effect`, `actions`, and `resources`. Resources can name the tenant, all workspaces, or one workspace. A change takes effect on the next operation.

## Temporary roles

A role gives a temporary credential. Create it with `create_iam_role` and a trust policy that names who may assume it: the tenant, a user, a group, or a service key. Attach policies with `attach_role_policy`, then the allowed caller uses `assume_role`. The session lasts 900 seconds to 12 hours (default one hour), is shown once, and is evaluated by the role's policies alone. The root user and role sessions cannot assume roles. Deleting a role revokes its sessions.

## Workspace access

A tenant user needs a policy that covers the workspace. To add a direct workspace role, use `grant_workspace_member` with the user's role for that workspace (Admin, Member, or Viewer; content ceilings `migration`, `write`, `read`), and `revoke_workspace_member` to remove it. `list_workspace_members` lists direct grants only. Revoking one also revokes the person's keys bound to that workspace.

A key's content scope also limits access; the effective permission is the narrower of the two. The `audit` grant is separate from the `read`, `write`, `schema`, `migration` scope ladder, and no policy or workspace role supplies it.

## Tenant and workspace administration

> Show the name and UUID of the connected tenant and workspace. Do not change anything.

Matching names can refer to different places. Check UUIDs with `whoami` before requesting changes.

| What you want to do                            | Tools                                                                      | Notes                                                                                |
| ---------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Change the tenant name or manual workspace cap | `get_tenant`, `update_tenant`                                              | Plan quotas do not change                                                            |
| Create, inspect, or delete a workspace         | `create_workspace`, `list_workspaces`, `get_workspace`, `delete_workspace` | Needs a tenant-scoped key; deletion removes data and the last workspace is protected |
| Rename a workspace or change its entity cap    | `update_workspace`                                                         | Changing the cap also needs tenant update permission                                 |
| Change your display name                       | `get_current_user`, `update_current_user`                                  | Needs a user-attributed key                                                          |

To change a manual cap, supply `replace_max_workspaces=true` with `max_workspaces` for a tenant, or `replace_max_entities=true` with `max_entities` for a workspace. Set the value to `null` to clear it. Omitting the field does not clear it, and plan quotas apply separately.

## Prepare a new workspace

A new workspace without a schema shows `schema_pending`. Creating the first schema changes the status to `active` and records that version in `schema_id`. Ask your assistant to check the workspace details before saving information.

Another workspace's embedding settings are not copied. Search may use the server's default provider if this workspace has no individual setting. Check the provider and whether search data is ready using [Embedding configuration](/wiki/configuration/embedding/). Setting a workspace provider after items have been saved rebuilds their search data.

## Management boundaries

- Creating a tenant from the command line, server-wide tenant inventory, and physical deletion need the server operator. See [Tenant retirement](/wiki/operations/tenant-retirement/).
- Server-wide user inventory and account deletion also belong to the operator, and leaving a tenant is separate.
- Archiving a schema does not physically delete its data. The shared template library is separate from physical PostgreSQL schemas. See [Templates](/wiki/guides/templates/#schema-versions-and-archival).
- Not every REST action is available through MCP. Marketplace publishing, inference jobs, sign-in/OAuth, Stripe webhooks, and server maintenance use their own procedures. Provider configuration neither runs inference nor removes licence restrictions.

`export_jsonl` maps to `GET /api/export.jsonl`; `import_jsonl` and `import_job_status` map to the import endpoints. See [Export and import](/wiki/guides/import-export/) for limits.

Through your assistant, use `capabilities` to inspect the key's permissions, `recall_context` to retrieve related information, `get_entity_drift` to compare an item with the active schema, or `discover_workspaces` to find accessible workspaces. `migration_dry_run` counts items that are current, behind without missing required values, or missing required values; it does not preview a proposed schema change.

After access is revoked, already-authenticated requests may finish. Queued work rechecks permission before writes, but not every external call already in progress can be stopped. See [API keys](/wiki/guides/api-keys/) for replacing credentials.
