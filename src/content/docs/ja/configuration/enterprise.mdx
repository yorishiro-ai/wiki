このページでは、Enterprise エディションの機能を説明します。利用にはライセンスキーが必要です。Community のすべての機能は Enterprise でも利用できます。

## ライセンス

`YORISHIRO_LICENSE_KEY` にライセンスキーを設定します。有効で期限内のライセンスがない場合、Enterprise エディションが許可するテナントは1つだけです。

## プランポリシーとジョブの上限

`YORISHIRO_PLAN_POLICY_ENABLED` の既定値は `false` で、`true` または `false` だけを受け付けます。`true` にすると、サブスクリプションのプランによってワークスペースとエンティティの上限が適用され、ターゲットごとに同時に実行できるバックグラウンドジョブの数も制限されます。

| 変数                                          | 既定値       | 説明                                                                                                                                       |
| --------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `YORISHIRO_WORKER_CLASS_SHARED_LIMIT`         | `1`          | デプロイ全体で同時に実行できる Shared ジョブの最大数                                                                                       |
| `YORISHIRO_WORKER_CLASS_TENANT_PRIVATE_LIMIT` | `1`          | 同時に実行できるテナント専用ジョブの最大数。テナントごとに数えます。                                                                       |
| `YORISHIRO_WORKER_OFFICIAL_LIMIT`             | プランによる | デプロイ全体で同時に実行できる Official ジョブの最大数です。この変数がない場合は、プランに従います: Free は `1`、Pro は `4`、Team は `8`。 |

各上限は正の整数にする必要があります。起動時には、プランポリシーが無効でもこれらの値を検査しますが、上限が適用されるのは有効な場合だけです。Official ジョブは、プランに関係なくまとめて1つの数として数えます。

これらの上限は、ワーカーの数や埋め込みプロバイダー自体の制限を変更しません。同時実行ジョブを増やすと、スループットが上がらないままデータベースの競合とメモリ使用量が増えることがあります。

Stripe のプランの価格は `YORISHIRO_STRIPE_PRICE_PRO` と `YORISHIRO_STRIPE_PRICE_TEAM` で対応づけます。変数を未設定のままにすると、その対応づけは行われません。

## Stripe の Webhook

Stripe の Webhook を処理するには、`YORISHIRO_STRIPE_WEBHOOK_SECRET` を設定します。各リクエストの `Stripe-Signature` は、生の本文に対して検証され、タイムスタンプの許容時間は300秒です。

## OAuth2 と OIDC のログイン

ID プロバイダーでのログインを有効にするには、`YORISHIRO_OAUTH_ISSUER_URL`、`YORISHIRO_OAUTH_CLIENT_ID`、`YORISHIRO_OAUTH_CLIENT_SECRET` を設定します。プロバイダーは、ループバックアドレスで動作する場合を除き、HTTPS を使う必要があります。

特にリバースプロキシの背後や、外部のポートが異なる場合は、`YORISHIRO_OAUTH_REDIRECT_URI` に公開コールバック URL を設定します。未設定の場合のコールバックは `http://<BINDING>:<PORT>/auth/oauth/callback` で、`0.0.0.0` のようなワイルドカードアドレスは `localhost` に置き換えられます。`YORISHIRO_BIND` が変更するのはこのフォールバックだけで、サーバーの待ち受け先は変わりません。

## ワークスペースごとの埋め込みプロバイダー

ワークスペースごとに、独自の埋め込みエンドポイントを使えます。割り当てには `PUT /api/workspace/embedding-key` を使います。

| フィールド              | 説明                                                             |
| ----------------------- | ---------------------------------------------------------------- |
| `base_url`              | 埋め込みエンドポイントの URL                                     |
| `model`                 | モデル名                                                         |
| `api_key`               | APIキー（`GET` では返されません）                                |
| `dimensions`            | モデルが生成するベクトルのサイズ                                 |
| `send_dimensions_param` | リクエストに `dimensions` を含めて送信します（既定値は `false`） |

## ワークスペースごとのワーカークラス

`PUT /api/workspace/worker-class` で、ワークスペースのバックグラウンドジョブをプールに割り当てます。

| フィールド     | 説明                                              |
| -------------- | ------------------------------------------------- |
| `worker_class` | `tenant_private`、`official`、`shared` のいずれか |

選択したターゲットのワーカーを実行してください。[ワーカーとキュー](../workers-and-queues/#ワーカーのターゲット)を参照してください。

## 非同期の infer-fill

infer-fill は、LLM を使ってフィールドの値を提案します。提案は、1件ずつ確認するまでは何も変更しません。

1. `PUT /api/workspace/llm-key` でワークスペースの LLM キーを設定します。設定していない場合、リクエストはジョブが作成される前に拒否されます。
2. `POST /api/schemas/active/{name}/infer-fill` で補完を開始します。レスポンスには `job_id` と、ステータス `queued` が含まれます。
3. ステータスが `completed` または `failed` になるまで、`read` キーで `GET /api/inference-jobs/{job_id}` をポーリングします。ジョブレコードにはステータス、提案された値・適用された値・スキップされた値の数、エラーメッセージが保持されるため、サーバーを再起動したあともポーリングできます。
4. `GET /api/inference-jobs/{job_id}/proposals` で提案を一覧表示します。
5. `POST /api/inference-jobs/{job_id}/confirm`、`/reject`、`/discard` で、提案を承認、却下、破棄します。これらには `schema` スコープが必要で、一覧表示には `read` が必要です。

モデルの回答は、それぞれ保留中の提案として保存されます。推測したデータをエンティティに書き込むことはありません。承認すると、統合後のエンティティがスキーマに対して検証され、`POST /api/migration-jobs/{job_id}/undo` で元に戻せるスナップショットが作成されます。古くなった提案や無効な提案には印が付けられ、エンティティは変更されません。

提案を操作できるのは、ジョブが `completed` になってからです。ジョブが失敗した場合、保留中の提案は自動的に破棄されます。完了した提案は、操作するまで確認できる状態のまま残ります。ジョブはキャンセルできず、期限切れにもなりません。

ワーカーがジョブの実行中に停止すると、ジョブは `running` のままになり、自動では再試行されません。再試行すると、最初の推論がまだ動作している間に2つ目の推論が始まる可能性があるためです。そのようなジョブは、再度開始する前に確認してください。

## スキーマのオリジンの更新

テンプレートから作成したワークスペースのスキーマは、以降のテンプレートの更新に追従できます。テンプレートが変更されると、リンクされたスキーマに更新保留中の印が付きます。確認と適用には、MCP ツールの `list_upstream_changes`、`merge_preview`、`merge_apply` を使います。[MCP ツール](../../reference/mcp-tools/)を参照してください。

プレビューには、フィールドの合計数、自動で追加または更新される項目、ローカルのフィールド、競合が表示されます。競合のないマージでは、新しいスキーマバージョンの作成と保留中の印の解除が同時に行われます。競合があるマージや失敗したマージでは、更新は保留のままです。

## スキーマのフォーク

Enterprise のワークスペースは、`POST /api/schema-forks` を使って、同じテナントの別のワークスペースから有効なスキーマバージョンを正確にコピーできます。フォークはテンプレートのオリジンから切り離され、独自のスキーマ履歴を持ちます。

`PUT /api/schema-forks/{fork_id}` は、ローカルの定義を更新するか、`action=follow` を指定してフォークをソースに再び合わせます。追従は同期的に行われます。ローカルの編集内容が破棄される場合は、`force=true` が必要です。

## テナントの再インデックススケジュール

テナントは、配下のすべてのワークスペースを一定の間隔で再インデックスできます。各実行は通常の再インデックスの流れ（`reindex_embeddings` と同じもの）を使うため、プロバイダーとモデルのバージョンの確認も同様に行われます。

スケジュールは `POST /api/identity/tenants/schedule` で設定します。ISO 8601 形式の期間（`P1D` は毎日、`P1W` は毎週、`PT6H` は6時間ごと）を指定します。IANA のタイムゾーン名も指定できます。既定は UTC です。間隔は `PT5M` 以上にしてください。年と月は指定できません。

最初の実行は、スケジュールを設定してから1間隔後です。実行のたびに、次の実行が1間隔後に予定されます。期限を過ぎた実行は、次のスケジューラーの tick で開始されます。猶予期間はありません。

スケジューラーは、サーバーやワーカーとは別のプロセスとして `yorishiro scheduler` で起動します。PostgreSQL では、同じデータベースを共有する複数のスケジューラーを起動できます。ロックを取れなかったレプリカは、その tick をスキップします。`DATABASE_URL` は PostgreSQL に直接接続するか、セッションモードのプーラーを経由してください。トランザクションモードのプーリングには対応していません。SQLite では、データベースファイルと同じ場所にある `.scheduler.lock` というファイルでロックを取ります。

実行は最大1回だけ発行されます。ジョブをキューに入れる前に、スケジュールを次の時刻へ進めます。その後にスケジューラーがクラッシュすると、その tick は実行されないことがあります。キューへの投入に失敗しても再試行されません。次の間隔が復旧の基準になります。

## SQLite のベクトル検索ベンチマーク

多くのエンティティを埋め込んだ SQLite では、ベクトル検索がすべてのベクトルをスキャンするため、遅くなることがあります。次のタスクで、実際のレイテンシーを計測できます。

```console
$ yorishiro task sqlite_ann_benchmark workspace_id:<uuid>
```

5回の検索について、中央値、最小値、最大値を報告します。ワークスペースのエンティティが1000件以上あり、中央値が200 ms を超える場合は、インデックス付きのベクトルテーブルを推奨します。しきい値は `min_entities` と `max_latency_ms` の引数で変更できます。このタスクは計測のみを行い、スキーマも設定も変更しません。
