Enterpriseを使うと、外部の認証サービスでのログインや、ワークスペースごとのAIサービスの選択ができます。日常の保存・検索はCommunityと同じです。このページのサーバー設定は運用者に依頼してください。自分で運用する場合はEnterprise（`ee`）のイメージかパッケージを使い、対象の機能に必要なライセンスを設定します。

## ライセンス

productionでは`YORISHIRO_LICENSE_KEY`を指定するか、設定ファイルの`initializers.licence_key`を編集します。有効で期限内のライセンスがなければ、利用できるのは1テナントです。SQLiteはライセンスがあっても1テナントに限られます。

パッケージでは秘密の値を保護した`production.yaml`に書きます。追加の環境ファイルは不要です。[パッケージ](../../installation/packages/#設定)を参照してください。

## OAuth2とOIDCのログイン

認証プロバイダーにYorishiroを登録し、次を設定します。

| productionの環境変数            | 設定ファイルの項目                 |
| ------------------------------- | ---------------------------------- |
| `YORISHIRO_OAUTH_ISSUER_URL`    | `initializers.oauth.issuer_url`    |
| `YORISHIRO_OAUTH_CLIENT_ID`     | `initializers.oauth.client_id`     |
| `YORISHIRO_OAUTH_CLIENT_SECRET` | `initializers.oauth.client_secret` |
| `YORISHIRO_OAUTH_REDIRECT_URI`  | `initializers.oauth.redirect_uri`  |

公開するリダイレクトURIを`/auth/oauth/callback`で終わる値として明示し、プロバイダーにも同じURIを登録してください。ローカルのループバックで試す場合を除きHTTPSを使います。既定のリダイレクト先はローカルの試用向けで、待受設定に従います。`HOST`では設定できません。MCPクライアントは引き続きAPIキーを使います。

ログインはブラウザーの認可画面から進め、MCPツールで代用しないでください。複数のワークスペースがあれば、名前だけでなくUUIDで接続先を確認します。招待の受諾には保存済みの本人情報が使われ、未検証のメールへの変更だけでは受諾できません。ログインできない場合は[ログインの復旧](../../operations/queue-start-objectives/#ログインの復旧)を参照してください。

## ワークスペースごとの埋め込みプロバイダー

`PUT /api/workspace/embedding-key`でワークスペース専用のサービスを指定できます。`base_url`、`model`、`api_key`、モデルの`dimensions`を設定し、`send_dimensions_param`はプロバイダーが必要とする場合だけ使います。設定を読み取ってもAPIキーは返りません。

モデルを変えると検索データの作り直しが必要です。[埋め込み](../embedding/#埋め込みモデルを変更する)に従い、埋め込みワーカーを起動しておいてください。

## ワークスペースごとのワーカークラス

`PUT /api/workspace/worker-class`の`worker_class`に`shared`、`official`、`tenant_private`を指定します。専用ワーカーを用意していなければ`shared`のままにしてください。

ほかのクラスを選ぶ前に、対象の2種類のワーカーを起動し、サーバーにも埋め込みの経路を宣言します。[ワーカーの対象](../workers-and-queues/#ワーカーの対象)を参照してください。宣言してもワーカーは起動されず、監視もされません。

## 非同期のinfer-fill

infer-fillはLLMで不足する値を提案し、確認するまで適用しません。スキーマの固定のデフォルト値ではなく、確認付きの提案が必要な場合に使います。

1. `PUT /api/workspace/llm-key`でLLMの認証情報を設定します。
2. `POST /api/schemas/active/{name}/infer-fill`で開始し、返された`job_id`を保存します。
3. `GET /api/inference-jobs/{job_id}`で`completed`か`failed`になるまで確認します。
4. `GET /api/inference-jobs/{job_id}/proposals`で提案を読み、内容を確認します。
5. `POST /api/inference-jobs/{job_id}/confirm`で承認するか、対応するエンドポイントでrejectまたはdiscardします。

承認も非同期で、新しい`job_id`が返ります。適用済みと判断する前に`GET /api/inference-jobs/confirmations/{job_id}`を確認してください。推論と承認には`job-target:shared`が必要です。一覧には`read`、確認操作と承認の状態取得には`schema`権限が必要です。

すべて適用されたと決めつけず、失敗や古くなった提案を確認してください。待機中というだけで再投入せず、[トラブルシューティング](../../operations/queue-start-objectives/)を確認します。

## テンプレートの更新とスキーマのフォーク

テンプレートに連携するスキーマでは、アシスタントに`list_upstream_changes`、続けて`merge_preview`を依頼します。特にローカルの項目を変更している場合は、`merge_apply`の前に内容を確認してください。競合があると更新は保留のままです。[組み込みテンプレート](../../guides/templates/)を参照してください。

`POST /api/schema-forks`では、同じテナントの別ワークスペースから有効なスキーマをコピーします。コピーは独立した履歴を持ちます。`PUT /api/schema-forks/{fork_id}`で元に追従し直すとローカルの変更が失われる場合があり、その場合は`force=true`が必要です。先に差分を確認してください。

## プランポリシーとジョブの制限

プラン別のサービスを運用しなければ`YORISHIRO_PLAN_POLICY_ENABLED=false`のままで構いません。有効にするとワークスペース、エンティティ、同時処理数のプラン制限が適用されます。

プラン別の制限にはEEと現在有効で認証済みのライセンス、`YORISHIRO_PLAN_POLICY_ENABLED=true`が必要です。利用するプランは認識できる有効なサーバーのライセンスプラン、テナントの課金プラン、Freeの順に選ばれます。手動の上限も設定されている場合は、プランの上限と比べて厳しい方が適用されます。Stripeとの連携で手動上限が上書きされることはありません。プランの制限を無効にしても、認証や明示的な運用上限は引き続き必要です。

`get_tenant_overview`は課金情報、使用量、保存された手動上限に加え、`active_plan` / `effective_max_workspaces`を別に返します。ワークスペースの詳細は`effective_max_entities`を別に返します。overviewにはテナントのAdmin/Ownerが必要で、課金状態は変更しません。

| productionの環境変数                          | 既定値   | 制限                                                 |
| --------------------------------------------- | -------- | ---------------------------------------------------- |
| `YORISHIRO_WORKER_CLASS_SHARED_LIMIT`         | `1`      | 共有の同時処理数                                     |
| `YORISHIRO_WORKER_CLASS_TENANT_PRIVATE_LIMIT` | `1`      | テナントごとの専用処理数                             |
| `YORISHIRO_WORKER_OFFICIAL_LIMIT`             | プラン別 | Officialの同時処理数。Freeは`1`、Proは`4`、Teamは`8` |

明示する値は正の整数です。ワーカーの起動数やプロバイダーの処理能力は増えません。設定ファイルでは`initializers.plan_policy_enabled`と`initializers.worker_admission`を使います。

Stripeと連携する場合は`YORISHIRO_STRIPE_WEBHOOK_SECRET`、`YORISHIRO_STRIPE_PRICE_PRO`、`YORISHIRO_STRIPE_PRICE_TEAM`、または対応する`initializers.stripe`の項目を設定します。Webhookの秘密の値は公開しないでください。

## MCPによる管理

接続済みのアシスタントに、表示する列やワークスペースのAIサービスの変更を依頼できます。変更前に接続先と現在の設定を確認してください。RESTでもMCPでも権限とライセンスの条件は同じです。サービス用のキーもスコープで許可されたワークスペース設定は変更できますが、本人のテナント管理者としては操作できません。

> このワークスペースのAIサービスとワーカーの設定を確認してください。秘密値は表示せず、まだ変更しないでください。

| 設定               | ツール                                                                                                   | コンテンツのスコープ                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| エンティティ表の列 | `list_entity_columns`, `set_entity_columns`, `reset_entity_columns`                                      | 一覧は`read`、変更は`write`。共有の表示設定でありスキーマ変更ではない                   |
| ワーカーの割り当て | `get_worker_class`, `set_worker_class`, `reset_worker_class`                                             | 取得は`read`、変更は`schema`。接続先の設定が必要                                        |
| 埋め込みprovider   | `get_embedding_provider`, `set_embedding_provider`, `reset_embedding_provider`                           | 秘密値を含まない取得は`read`、変更は`schema`。全体のreindexを同一トランザクションで投入 |
| 推論provider       | `get_llm_provider`, `set_llm_provider`, `reset_llm_provider`                                             | 秘密値を含まない取得は`read`、変更は`schema`。推論は実行しない                          |
| スキーマfork       | `create_schema_fork`, `list_schema_forks`, `get_schema_fork`, `update_schema_fork`, `delete_schema_fork` | 取得は`read`、変更は`schema`。選択中のワークスペースが所有するものだけ                  |

登録済みのproviderの秘密値は取得できません。ワーカーの割り当てをリセットするとsharedに戻りますが、待機中のジョブは元の経路のまま処理されます。接続先が設定されていても、ワーカーが動いているとは限りません。

forkを更新するときは、変更元の最新状態と履歴、循環が確認されます。ローカルの編集を破棄して元に追従する場合は`force`が必要なので、先に差分を確認してください。forkを削除しても元のスキーマは残り、エンティティから参照されている場合は削除が保護されます。

providerの設定は推論を実行せず、ライセンスの制限も解除しません。Marketplace公開、推論ジョブ、OAuth/Stripe、stream export、デプロイ保守は管理MCPとの対応範囲外です。[管理操作の境界](../../guides/access-management/#管理操作の境界)を参照してください。
