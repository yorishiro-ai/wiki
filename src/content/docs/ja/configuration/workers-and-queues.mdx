Yorishiro は埋め込みの同期や再インデックスなど時間のかかる処理をバックグラウンドジョブとして実行します。サーバーがジョブをキューに入れ、別のワーカープロセスがそれを実行します。

## プロセス

HTTP サーバーとワーカーは、別々のプロセスとして実行します。`yorishiro start` だけを実行した場合はサーバーのみが動き、ジョブは処理されません。

| プロセス       | コマンド                                        |
| -------------- | ----------------------------------------------- |
| サーバー       | `yorishiro start`                               |
| ワーカー       | `yorishiro start --worker=worker-target:shared` |
| スケジューラー | `yorishiro scheduler`                           |

パッケージと Docker Compose の例では、3つすべてを起動します。個人での利用にはこれで十分です。スケジューラーは中断したジョブの回復と、設定されたスケジュールタスクの実行を担当します。専用のプロセスとして実行してください。

引数なしの `--worker`、`--all`、`--server-and-worker` は拒否されます。

すべてのプロセスに、ジョブが使うデータベース、キュー、埋め込みの設定を同じ内容で用意する必要があります。ワーカーはサーバーと同じホストでも、別のマシンでも実行できます。別のマシンのワーカーは同じ `QUEUE_URL` を使う必要があります。この URL が共有の SQLite ファイルを指す場合は、絶対パスを使ってください。相対パスはホストごとに別々に解決されるためです。

## ワーカーのターゲット

各ジョブは1つのターゲットに属し、各ワーカーは選択したターゲットを処理します。

- `worker-target:shared`: 既定のプールです。クエリの埋め込みと Enterprise の infer-fill は、常にここで実行されます。
- `worker-target:official`: Official ジョブ（Enterprise）
- `worker-target:tenant:<tenant-id>`: 1つのテナントのジョブ。ワークスペース ID ではなく、テナントの小文字でハイフン区切りの UUID を使います。

```console
$ yorishiro start --worker=worker-target:official
$ yorishiro start --worker=worker-target:tenant:0198f3a0-0000-7000-8000-00000000000a
```

ターゲットをカンマで区切って列挙すると、1つのプロセスで複数のターゲットを処理できます。ただし、特定のターゲットのための処理能力が確保されるわけではありません。Official ワーカーとテナントのワーカーは、プロセスマネージャーなどから自分で起動してください。Yorishiro は自動では起動しません。

Enterprise ではワークスペースのジョブをプールに割り当てられます。[Enterprise の設定](../enterprise/#ワークスペースごとのワーカークラス)を参照してください。

### ワーカーのルーティングを安全に変更する

どのワーカーがどのターゲットを処理するかを変更する前に、ジョブを作成する処理を停止し、対応するワーカーが、キュー済み、実行中、再試行中のジョブをすべて完了するまで待ちます。そのあとで、新しいルーティングでワーカーを起動してください。サーバーとワーカーが同時に異なるルーティングを使うと、ジョブが未処理のまま残ることがあります。

Valkey では、テナントのターゲットごとに、最初のジョブが届いた時点で専用のキューが作成されます。テナントを削除しても、そのキューは削除されません。使わなくなったテナントのキューは、空になり、そのテナントを処理しなくなってから、自分で削除してください。

## ワーカーの設定

| 変数                                 | 既定値                                  | 説明                                                  |
| ------------------------------------ | --------------------------------------- | ----------------------------------------------------- |
| `YORISHIRO_QUEUE_WORKERS`            | SQLite のキューでは `1`、それ以外は `2` | 1つのワーカープロセス内で並行して動くジョブループの数 |
| `YORISHIRO_QUEUE_REAPER_AGE_MINUTES` | `30`                                    | 処理中のままのジョブが回復されるまでの時間            |
| `DB_MAX_CONNECTIONS`                 | SQLite では `10`、PostgreSQL では `100` | データベース接続プールのサイズ                        |

これらの変数は production の設定に適用されます。development の設定では固定値が使われます。

SQLite では書き込みを行えるのは1つだけです。SQLite のキューでワーカーを増やしても、競合が増えるだけで速くなりません。その場合、起動時に警告をログに出力します。SQLite の接続プールが16を超えるときにも警告が出ます。SQLite のデータベースと Valkey のキューの組み合わせも動作しますが、リモートのワーカーは SQLite ファイルを開けないため、ワーカーはデータベースと同じホストに置いてください。

スループットを最大にするには、データ用に PostgreSQL、キュー用に Valkey を使います。次に速いのはデータとキューの両方に PostgreSQL を使う構成で、両方に SQLite を使う構成が最も遅くなります。PostgreSQL では、複数のワーカープロセスが同時にジョブを取得できます。SQLite では、ジョブの取得が直列化されます。

## キューの優先度

ジョブが待機している場合、Yorishiro はテナント専用のジョブ、Official ジョブ、Shared ジョブの順に実行します。優先度の低いジョブが1分間待機した場合、同じワーカーを使う新しい優先度の高いジョブは、待機中のジョブが開始されるまで Shared ジョブの後ろに回されます。すでにキューにあるジョブの優先度は変わりません。

## 同時実行ジョブの制限

Community ではターゲットごとの同時実行ジョブ数を制限しません。Enterprise では制限できます。[Enterprise の設定](../enterprise/#プランポリシーとジョブの上限)を参照してください。

ジョブの待機時間とログの読み方については、[キュー開始時間](../../operations/queue-start-objectives/)を参照してください。
