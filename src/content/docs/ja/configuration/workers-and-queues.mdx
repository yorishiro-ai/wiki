[Composeの例](../../installation/docker-compose/)や[パッケージ](../../installation/packages/)を使う場合は、4つのサービスを起動してください。個人利用では専用のワーカープールは不要です。

## プロセス

| サービス               | コマンド                                        | 担当する処理                                               |
| ---------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| サーバー               | `yorishiro start`                               | APIとMCPのリクエスト                                       |
| 埋め込みワーカー       | `yorishiro start --worker=worker-target:shared` | 埋め込みの更新、検索文の埋め込み、再インデックス           |
| アプリケーションジョブ | `yorishiro start --worker=job-target:shared`    | インポート、デフォルト値の補完、取り消し、Enterpriseの推論 |
| スケジューラー         | `yorishiro scheduler`                           | 回復と定期処理                                             |

2種類のワーカーは別々のプロセスで動かします。1つのコマンドに`worker-target:*`と`job-target:*`を混在させないでください。対象のない`--worker`、`--all`、`--server-and-worker`は使えません。

すべてのサービスでデータベース、キュー、処理に必要なプロバイダーの設定をそろえてください。データベースかキューがSQLiteなら、同じホストで同じファイルの絶対パスを使います。別マシンのワーカーにはPostgreSQLのデータベースと、PostgreSQLかValkeyのキューが必要です。

## ワーカーの対象

Enterpriseのワークスペースに専用の処理能力を割り当てたい場合だけ変更します。対象はワーカーが処理する仕事を指定するもので、ワーカーを自動起動する設定ではありません。

| プール        | 埋め込みワーカーの引数                      | アプリケーションジョブの引数             |
| ------------- | ------------------------------------------- | ---------------------------------------- |
| 共有          | `--worker=worker-target:shared`             | `--worker=job-target:shared`             |
| Official      | `--worker=worker-target:official`           | `--worker=job-target:official`           |
| 1つのテナント | `--worker=worker-target:tenant:<tenant-id>` | `--worker=job-target:tenant:<tenant-id>` |

IDには小文字とハイフンで表したテナントのUUIDを使います。ワークスペースのIDではありません。検索文の埋め込みと推論には共有サービスが必要なため、共有ワーカーも残してください。

専用プールを割り当てる前に、次を行います。

1. サーバーと同じ設定で、対応する埋め込みワーカーとアプリケーションジョブを起動します。
2. サーバーの`settings.worker_targets`に埋め込みの対象を追加し、`worker-target:shared`も残します。productionの`YORISHIRO_WORKER_TARGETS`には`["worker-target:shared","worker-target:official"]`のようなJSON配列を指定できます。
3. 対象を宣言した設定でサーバーを再起動し、`PUT /api/workspace/worker-class`でワークスペースに割り当てます。[Enterprise設定](../enterprise/#ワークスペースごとのワーカークラス)を参照してください。

この宣言は稼働確認ではありません。プロセスの監視は別途必要です。割り当てを削除、変更する場合は、新しい処理の受付を止め、古いワーカーの処理が完了してから置き換えてください。

同じ種類の対象なら、カンマで区切って1つのプロセスに指定できます。その場合は処理能力を共有し、対象ごとには確保されません。

## ワーカーの設定

変更する前に[トラブルシューティング](../../operations/queue-start-objectives/)を確認してください。モデルやデータベースに接続できない問題は、ワーカーの数を増やしても解決しません。

| productionの環境変数                 | 既定値                           | 用途                                               |
| ------------------------------------ | -------------------------------- | -------------------------------------------------- |
| `YORISHIRO_QUEUE_WORKERS`            | SQLiteキューは`1`、それ以外は`2` | ワーカープロセスごとの同時処理数                   |
| `YORISHIRO_QUEUE_REAPER_AGE_MINUTES` | `30`                             | 処理中のまま残ったキューの仕事を回収するまでの分数 |
| `DB_MAX_CONNECTIONS`                 | SQLiteは`10`、PostgreSQLは`100`  | 設定したデータベースプールごとの最大接続数         |

SQLiteは同時に1つしか書き込めません。同時書き込みが問題になる場合は、ワーカーを増やすよりPostgreSQLを選んでください。Enterpriseでは[同時実行数の制限](../enterprise/#プランポリシーとジョブの制限)も設定できます。
