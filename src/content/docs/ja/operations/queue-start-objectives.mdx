まずサービスの状態とクライアントに返されたエラーを確認してください。サーバー、埋め込みワーカー、アプリケーションジョブ、スケジューラーを、同じデータベースとキューの設定で動かします。

## 接続できない

1. サーバーのホストで`curl http://localhost:5150/_ping`を実行します。ポートを変えている場合はURLも変更してください。
2. 失敗する場合は、サーバーの起動状態とログを確認します。
3. ローカルでは接続でき、外部からは失敗する場合は、Dockerの公開ポート、`BINDING`、ファイアウォール、リバースプロキシを確認します。クライアントの`localhost`ではなく、サーバーのアドレスを使ってください。
4. MCPには`/mcp`と`Authorization: Bearer <api-key>`ヘッダーを使います。ホスト名とブラウザーの接続元は[設定](../../configuration/#サーバーのアドレス)を確認してください。

`/_ping`はHTTPプロセスの確認です。検索やジョブの動作までは確認しません。

## 認証や権限のエラー

`401`では、キーが欠けていないか、失効していないか、Bearerヘッダーが正しいかを確認してください。`403`やツールの権限エラーでは、その操作が許可されているか管理者に確認します。スキーマ作成とインポートには`schema`、読み取りには`read`権限が必要です。

キーの問題を直すために環境を作り直さないでください。新しいキーを受け取り、MCPクライアントの設定を更新します。

## 検索が503になる

サーバーだけでなく、先に埋め込みワーカーを確認します。

```sh
docker compose ps
docker compose logs --tail 100 worker
```

パッケージの場合は次を使います。

```sh
sudo systemctl status yorishiro-worker
sudo journalctl -u yorishiro-worker -n 100 --no-pager
```

初回起動時のモデルのダウンロード中なら完了を待ちます。空き容量、モデルの読み取り権限、外部の埋め込みサービスへの接続も確認してください。`none`で無効にしている場合は、意味による検索の前にプロバイダーを有効にします。

ワークスペースの再インデックス中も`503`になります。正常に完了するまで待ってください。プロバイダーの障害を直したあとは[埋め込みの回復手順](../../configuration/embedding/#埋め込みモデルを変更する)を参照してください。

## 保存した項目が検索に出ない

IDを指定した取得や一覧をアシスタントに依頼してください。検索データはバックグラウンドで更新されるため、保存成功直後に類似検索できるとは限りません。長く続く場合は埋め込みワーカーのログを確認します。

## インポートなどが待機中のまま

インポート、デフォルト値の補完、取り消し、Enterpriseの推論にはアプリケーションジョブのワーカーが必要です。埋め込みワーカーでは実行しません。

```sh
docker compose logs --tail 100 jobs
```

パッケージの場合は次を使います。

```sh
sudo systemctl status yorishiro-jobs yorishiro-scheduler
sudo journalctl -u yorishiro-jobs -u yorishiro-scheduler -n 100 --no-pager
```

`start --worker=job-target:shared`が動き、すべてのサービスでデータベースとキューがそろっているか確認します。インポートは繰り返し投入せず、返された`job_id`で`import_job_status`を呼び出してください。

Enterpriseの専用プールでは、[対象の宣言とワーカーの起動](../../configuration/workers-and-queues/#ワーカーの対象)を両方確認します。宣言があってもワーカーが動いているとは限りません。制限が有効なら、実行中の処理が終わるまで待機する場合があります。

## サービスが再起動できない

再試行する前にログの原因を直してください。systemdの再起動上限に達した場合は次を実行します。

```sh
sudo systemctl reset-failed yorishiro-worker
sudo systemctl start yorishiro-worker
```

ユニット名は失敗しているサービスに置き換えます。設定の構文、接続URL、読み取り権限を確認してください。調査のためにデータベースやキューのファイルを削除しないでください。

## 問い合わせる

リリースタグ、エディション、導入方法、データベースとキューの種類、失敗した操作、関係するエラーメッセージを添えてください。APIキー、パスワード、非公開の内容は取り除きます。動いているサービスと、APIに直接リクエストしても発生するかも伝えてください。
