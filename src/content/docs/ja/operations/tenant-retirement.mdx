無効化と削除は別の操作です。無効化ではデータと上限の占有が残ります。物理削除は取り消せず、デプロイを管理するoperatorの操作が必要です。どちらの場合も先にバックアップを取り、対象を確認してください。共有する例に本番のテナントUUIDや秘密値を含めないでください。

## 無効化前の確認

Ownerは`GET /api/tenants/current/retirement`または`tenant_retirement_inventory`で確認できます。共有の本人アカウント、未完了の処理、保持される記録、外部のスキーマforkを確認してください。この一覧はその時点の情報であり、後続の操作の許可を保証しません。外部のforkは完全削除前に明示的な解決が必要な場合があります。

## データを残して無効化する

Ownerは`POST /api/tenants/current/disable`の`confirmed_tenant_id`に現在のテナントUUIDを指定するか、MCPの`disable_tenant`で同じ確認を行います。OwnerではないテナントのAdminには無効化できません。

無効化すると、呼び出し元を含むテナントのキーが失効し、未完了の処理が取り消されます。データと上限の占有は残ります。認証済みの通常リクエストは完了する場合があり、すでに進行中の外部呼び出しをすべて取り消せるわけではありません。無効化により外部への作用がすべて即時停止するとは保証しないでください。

## operatorによる完全削除

operator CLIには次のタスクがあります。

| タスク                      | 引数と用途                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------ |
| `inspect_tenant_retirement` | `tenant_id`。保持データと影響を確認                                                              |
| `disable_tenant`            | 同じ値の`tenant_id`と`confirmed_tenant_id`。データを残して無効化                                 |
| `delete_tenant`             | 同じ値の`tenant_id`と`confirmed_tenant_id`。事前の無効化が必要で、テナントのデータを不可逆に削除 |

開発用データベースを誤って対象にしないよう、目的のデプロイの設定で実行してください。テナントに紐付くREST/MCPのキーでは物理削除できません。通常のワークスペース削除では最後の1つが保護されます。明示的なテナント廃止は別の削除手順であり、通常のワークスペース削除で代用するものではありません。

完全削除では実際のデータ削除によりテナントの占有枠を解放します。保持データとAPIキーの履歴は削除されますが、共有の本人アカウントと秘密値を含まない廃止の記録は残ります。全体のユーザー削除とは別の操作です。

## 本人アカウントの削除

テナントのメンバーを削除すると本人に紐付くテナントのキーは失効しますが、共有アカウントは削除されません。全体のユーザー一覧はoperatorの`list_users`で確認します。`delete_user`にはテナントのメンバー資格がゼロであることと、同じ値の`user_id` / `confirmed_user_id`が必要です。残った本人のキーを失効させてから紐付けを外し、本人アカウントを削除します。テナントの管理者は、メンバー管理によってほかのテナントの本人アカウントを削除することはできません。

## 上限と検証範囲

保持された占有と、plan quotaや手動の上限を混同しないでください。[Enterprise設定](../../configuration/enterprise/#プランポリシーとジョブの制限)を参照してください。
