この手順はキューのプロバイダーを切り替えるときに使います。キューに残っている作業を新しいパブリッシャーのエポックへ移します。

## 手順

1. 生産者による直接の発行を止めるリリースをデプロイします。
2. 古い生産者とワーカーをすべて停止します。運用者の証明として `old_workers_exited:true` を記録します。
3. 発行を一時停止します。エポックは `<n>` から E に進みます。以降の手順では E を使います。

   ```console
   $ yorishiro task set_queue_publishing_epoch expected_epoch:<n> active:false
   ```

4. 発行が停止している間に、プロバイダーのスナップショットの証拠を記録し、再投入を準備します。

   ```console
   $ yorishiro task replay_queue_dispatch_snapshot phase:prepare expected_epoch:<E> old_workers_exited:true cutoff_at:<RFC3339> snapshot_id:<evidence-id>
   ```

5. 新しいワーカープールを起動し、準備済みのエポックを有効にします。

   ```console
   $ yorishiro task replay_queue_dispatch_snapshot phase:activate expected_epoch:<E> old_workers_exited:true snapshot_id:<evidence-id>
   ```

   有効化には prepare と同じ `expected_epoch:<E>` と `snapshot_id` を渡します。prepare が記録したカットオフも必要です。そのうえで発行を再開します。

6. 有効化が完了するまで生産者は停止したままにします。完了してから生産者を起動します。

## prepare の動作

- 待機中、再試行待ち、実行中の作業と、期限内の保留中のクエリ埋め込みの作業を、新しいエポックに移します。
- 発行の一時停止中に受け付けた作業も含めます。
- 予定されている再試行の時刻は変わりません。実行中のジョブは古いリースの期限を待たずに回収されます。

## 制限

- 証明とスナップショット ID は、運用者が提供する証拠です。Yorishiro は検証しません。
- 隔離されたジョブと、待機中、再試行待ち、実行中のいずれでもなくなったジョブは、エラーなしでスキップされます。ライフサイクルがない期限切れのクエリ埋め込みのジョブも同様にスキップされます。
- ライフサイクルがなく、まだ発行されておらず、ワークスペースと期限を持つクエリ埋め込みの行ではない古い行があると、prepare は `N lifecycle-less dispatch rows cannot be replayed safely` で失敗します。その行を隔離するか、ほかの方法で解決してから、prepare を再実行してください。
- エポックを変えても、プロバイダーが受け付け済みのメッセージは取り消せません。プロバイダーのタイムアウトやクラッシュ、結果が不明な投入によって、作業が重複する場合があります。
