この手順は、キューのプロバイダーを切り替えるときに使います。キューに残っている作業を新しいパブリッシャーのエポックへ移します。

## 投入の仕組み

アプリケーションは、業務上の変更とディスパッチ用のアウトボックス行を同じトランザクションでコミットします。アウトボックス行をキューへ発行するのは、ディスパッチリレーだけです。リレーはデータベースのトランザクションの外でプロバイダーを呼び出します。プロバイダーのタイムアウトやクラッシュが起きると、同じジョブが二度発行される場合があります。

## 手順

1. 生産者による直接の発行を止めるリリースをデプロイします。
2. 古い生産者とワーカーをすべて停止します。運用者の証明として `old_workers_exited:true` を記録します。
3. 発行を一時停止します。エポックは E に進みます。

   ```console
   $ yorishiro task set_queue_publishing_epoch expected_epoch:<n> active:false
   ```

4. 発行が停止している間に、プロバイダーのスナップショットの証拠を記録し、再投入を準備します。

   ```console
   $ yorishiro task replay_queue_dispatch_snapshot phase:prepare expected_epoch:<E> old_workers_exited:true cutoff_at:<RFC3339> snapshot_id:<evidence-id>
   ```

5. 新しいワーカープールを起動し、準備済みのエポックを有効にします。

   ```console
   $ yorishiro task replay_queue_dispatch_snapshot phase:activate expected_epoch:<E> old_workers_exited:true snapshot_id:<evidence-id>
   ```

   有効化では、エポックが E のままであることを確認します。そのうえで、準備済みの E+1 を、エポックをさらに進めずに有効にします。

6. 有効化が完了するまで生産者は停止したままにします。完了してから生産者を起動します。

## prepare の動作

- 待機中、再試行待ち、実行中、期限内の保留中のクエリ埋め込みの作業を E+1 に付け替えます。
- 発行の一時停止中に受け付けた作業も含めます。
- 将来の `retry_at` は変更しません。実行中の行は、古いリースの期限を待たずに回収します。

## 制限

- 証明とスナップショット ID は、運用者が提供する証拠です。Yorishiro は検証しません。
- 隔離された行、期限切れの行、表現できない古い行は再投入されません。別途照合してください。
- エポックを変えても、プロバイダーが受け付け済みのメッセージは取り消せません。結果が不明な投入は、作業が重複する場合があります。
