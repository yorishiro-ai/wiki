更新前に対象リリースの説明を読み、データベースと設定をバックアップしてください。情報の移動にはエクスポートを使えますが、環境全体のバックアップにはなりません。

## バックアップする

- SQLite: 4つのサービスを止めてからデータディレクトリをコピーします。データベース、別ファイルのキューデータベース、SQLiteの付随ファイルを一緒に残してください。使用中の`.sqlite3`だけをコピーしないでください。
- PostgreSQL: `pg_dump`など、環境のバックアップ手順を使い、別のデータベースへの復元を試してください。キューが別のデータベースやValkeyなら、そのバックアップも必要です。
- 設定: Composeファイルや`/etc/yorishiro/production.yaml`、接続設定、認証情報を保護したバックアップに保存します。

イメージやパッケージのバージョンも記録してください。モデルは再ダウンロードできますが、残しておくと大きなダウンロードを避けられます。

## Docker Composeを更新する

1. クライアントから新しい処理が入らないようにし、可能なら待機中のジョブが終わるまで待ちます。
2. サービスを停止してバックアップを取ります。既存のボリュームは残してください。
3. `compose.yml`のイメージタグを対象のバージョンに変更します。4つとも同じバージョンとエディションを使います。
4. 取得して起動します。

```sh
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail 100 app worker jobs scheduler
```

`/_ping`、認証付きの読み取り、検索を確認してからクライアントの利用を再開します。`docker compose down -v`は名前付きボリュームを削除するため、実行しないでください。

## パッケージを更新する

新しい処理を止め、4つのサービスを停止してバックアップを取ります。[パッケージの導入コマンド](../../installation/packages/)で新しいパッケージをインストールしてください。設定を新しい`/etc/yorishiro/production.yaml.example`と比較してから再起動します。

```sh
sudo systemctl restart yorishiro yorishiro-worker yorishiro-jobs yorishiro-scheduler
```

## 復元や保存先の変更

環境を置き換える前に、別の環境で復元を試してください。データベースの移行後は、古いバイナリで読めない場合があります。イメージタグを戻すだけで復旧できるとは限りません。リリースごとの手順に従い、必要なら対応するバックアップを復元します。

ワークスペースの情報を移す場合は[エクスポートとインポート](../../guides/import-export/)を使います。`DATABASE_URL`や`QUEUE_URL`を変更しても、データや待機中のジョブは移りません。検証済みの移行手順がないまま、処理が残るキューを切り替えないでください。

古いドキュメントにあった発行エポックの切替タスクは現在の製品にはありません。更新に使わないでください。
