この手順は[PR #598](https://github.com/yorishiro-ai/yorishiro/pull/598)のマージ後のproduct `develop` に対応します。テナントとワークスペースはUUIDで識別し、名前は表示用に使います。権限を変更する前に、`whoami`で接続先を確認してください。

## 役割と実効権限

利用者に紐付くキーのコンテンツ操作権限は、保存されたスコープ、テナントの役割、ワークスペースの権限のうち最も狭い範囲になります。広いスコープのキーでも役割の制限を超えられず、昇格してもキーに保存されたスコープは広がりません。`audit` grantは、`read` → `write` → `schema` → `migration` の順序とは独立しています。

| テナントの役割 | コンテンツ操作の上限 | ワークスペースへのアクセス     |
| -------------- | -------------------- | ------------------------------ |
| Owner / Admin  | `migration`          | テナント内の管理権限を継承     |
| Member         | `write`              | 直接のワークスペース権限が必要 |
| Viewer         | `read`               | 直接のワークスペース権限が必要 |

ワークスペースに直接付与する役割はAdmin（上限`migration`）、Member（`write`）、Viewer（`read`）です。テナントの役割による上限も適用されます。たとえば、テナントのMemberにワークスペースのAdminを付与すると直接の権限を管理できますが、コンテンツの`schema`権限は得られません。`list_workspace_members`は直接の権限を一覧し、Owner/Adminから継承した権限は含めません。チームはこの利用者ごとの権限付与の対象外です。

ワークスペースのAdminは`list_workspace_members`、`grant_workspace_member`、`revoke_workspace_member`で直接の権限を一覧、付与・変更、取り消しできます。対象者はそのテナントのメンバーである必要があります。この役割では、テナントのメンバー管理、キー発行、所有権移譲、課金管理はできません。直接の権限を取り消すと、継承したアクセスがない場合は対象のワークスペースに紐付くキーも失効します。テナントのメンバー資格は削除されません。

サービス用のキーには本人の役割がありません。スコープ、ワークスペースへの紐付け、テナントの有効状態、有効期限は引き続き適用されます。本人として管理操作を行ったり、本人のプロフィール用ツールを使ったりはできません。管理者の役割だけでaudit権限が付くこともありません。

## 共同利用者を招待する

テナントのAdminまたはOwnerは、サーバーのシェルを使わずに招待を管理できます。

1. `create_invite`に相手のメールアドレス、テナントの役割、有効期限を指定します。Ownerとして招待できるのはOwnerだけです。
2. 返されたトークンを非公開の方法で相手に渡します。Yorishiroから招待メールが自動送信されるわけではありません。
3. 相手は招待を使って登録するか、既存の本人の認証情報で受諾します。`accept_invite`には、保存済みの宛先メールアドレスが一致する本人のアカウントが必要です。サービス用のキーでは受諾できません。受諾してもログイン用の認証情報は発行されず、選択中のワークスペースも変わりません。
4. MemberまたはViewerには、利用するワークスペースの権限も明示的に付与します。テナントに参加しただけでは非公開のワークスペースにアクセスできません。

`list_invites`はトークンを含まない招待の一覧を返します。未使用の招待は`revoke_invite`で取り消せます。`reissue_invite`に新しい期限を指定すると古いトークンが無効になり、相手に渡すための新しいトークンが返ります。メールの再送機能ではありません。

RESTでは`POST` / `GET /api/members/invites`、`DELETE /api/members/invites/{invite_id}`、`POST /api/members/invites/{invite_id}/reissue`を使います。パスワードでのログイン、登録、OAuthは認証用エンドポイントであり、MCPツールではありません。未検証で変更可能なメールアドレスだけでは本人確認になりません。

## メンバーと所有権の変更

`list_members`と`set_member_role`で既存のアカウントを追加し、テナントの役割を変更できます。RESTでは`POST /api/members`に`email`と`role`を指定します。この操作は既存のアカウントを参加させるもので、共有の本人アカウントは作成しません。未登録の相手には招待を使ってください。

変更前に`preview_member_role_change`または`preview_member_removal`で影響を確認します。プレビューはその時点のワークスペースとキーへの影響を示し、後続の変更の許可を保証しません。`remove_member`（`DELETE /api/members/{user_id}`）はメンバー資格と本人に紐付くテナントのキーを失効させますが、共有の本人アカウントは残します。

Ownerの権限を付与・削除できるのはOwnerだけです。同時に変更した場合も、最後のOwnerは削除・降格できません。`transfer_ownership`（`POST /api/members/transfer-ownership`）は既存のメンバーに所有権を移し、呼び出した本人をAdminにする処理を一括で行います。確定前に後任のUUIDを確認してください。

## テナントとワークスペースの管理

| 作業                                         | MCPツール                                                                                      | 権限と制限                                                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 現在のテナントの取得・変更                   | `get_tenant`, `update_tenant`                                                                  | テナントのAdmin/Owner。名前と手動のワークスペース上限を変更でき、plan quotaは変更しない                        |
| ワークスペースの作成・一覧・取得・変更・削除 | `create_workspace`, `list_workspaces`, `get_workspace`, `update_workspace`, `delete_workspace` | 作成・削除はテナントのAdmin/Owner。最後のワークスペースは削除できず、削除するとそのデータも失われる            |
| ワークスペースの基本情報                     | `update_workspace`                                                                             | 名前はワークスペースのAdmin、手動のエンティティ上限はさらにテナントのAdminが必要。スキーマの紐付けは変更しない |
| 自分のプロフィール                           | `get_current_user`, `update_current_user`                                                      | 本人に紐付くキーのみ。テナント間で共有する表示名だけを扱い、メール・パスワード・OAuthは変更しない              |

選択中のワークスペースの取得・変更・スキーマ操作では、キーに紐付いた対象を切り替えられません。直接の権限管理とワークスペース削除は、操作ごとの役割検証のもとで同じテナント内の対象を明示します。これは、紐付いたキーの接続先を自由に変更できるという意味ではありません。キーの管理は[APIキー](../api-keys/)、Ownerによる無効化は[テナントの廃止](../../operations/tenant-retirement/)を参照してください。

手動の上限を置き換え・解除する場合は、テナントでは`replace_max_workspaces=true`、ワークスペースでは`replace_max_entities=true`を指定し、対応する`max_workspaces` / `max_entities`に値を指定します。解除する値は`null`です。上限を省略するだけでは解除されません。plan quotaは別に適用されます。

## 管理操作の境界

対応する管理操作はこのページと[MCPツール](../../reference/mcp-tools/)のとおりREST/MCPで使えますが、すべてのREST操作にMCP版があるわけではありません。

- テナントの作成、デプロイ全体のテナント一覧、テナントの物理削除はoperator CLIの操作です。テナントに紐付くMCPでは行いません。
- 全体のユーザー一覧と削除もoperator CLIです。削除にはテナントのメンバー資格がゼロであることと、同じユーザーUUIDによる確認が必要です。本人への紐付けを外す前に残ったキーを失効させます。メンバーの削除と本人アカウントの削除は別の操作です。
- ワークスペースのスキーマは不変のバージョンと非破壊のarchiveで管理します。テナントで共有するtemplate libraryの定義は別の資源であり、物理的なPostgreSQL schemaではありません。[テンプレートとスキーマの管理](../templates/#スキーマのバージョンとarchive)を参照してください。
- Marketplace公開、推論ジョブ実行、ブラウザーのログイン・OAuth、Stripe webhook、stream export、デプロイ保守は管理MCPとの対応範囲外です。provider設定ツールは推論を実行せず、ライセンスの制限も解除しません。

権限を変更しても、認証済みの通常リクエストは完了する場合があります。キューの処理は書き込み・公開前に権限を再確認しますが、すでに進行中の外部呼び出しをすべて取り消せる保証はありません。
