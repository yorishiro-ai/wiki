テナントは組織や個人の利用範囲、ワークスペースはその中で情報を分けて保存する場所です。テナントにはrootユーザーが1人いて、ほかの人は権限をIAMポリシーで決めるテナントユーザーです。このページの操作は、rootユーザーまたは管理者に依頼してください。

## サインインする

| 対象                 | 方法                                                                            |
| -------------------- | ------------------------------------------------------------------------------- |
| 新しいテナントのroot | `POST /auth/signup`に`email`、`password`、任意の`display_name`を指定            |
| 既存のrootユーザー   | `POST /auth/root/login`に`email`と`password`を指定                              |
| テナントユーザー     | `POST /auth/tenant/login`に`x-tenant-id`ヘッダー、`user_name`、`password`を指定 |

サインアップではテナントとrootユーザーが作成され、キーは発行されません。ログインのたびに、テナントに紐付くAPIキーが一度だけ返されます。このキーはワークスペースに紐付かないため、[APIキー](../api-keys/)の手順で`X-Workspace-Id`を指定します。ほかのテナントに属さないrootアカウントは、テナントを廃止しても残ります。

## 人を追加・削除する

> `alice`というテナントユーザーを作成してください。ポリシーを付ける前に、権限の内容を見せてください。

`create_tenant_user`には`user_name`（英数字、`.`、`_`、`-`で1〜64文字）、12文字以上のパスワード、任意の`display_name`を指定します。作成直後のユーザーには、ポリシーを付けるかグループに追加するまで権限がありません。メンバーは`list_members`で確認し、パスワードは`reset_tenant_user_password`で置き換えます。この操作では、その人のキーがすべて失効します。rootの復旧は運用者の作業です。

削除する前に`preview_member_removal`で影響を確認します。`remove_member`は本人に紐付くキーを失効させ、テナントユーザーのアカウントもメンバー資格と一緒に削除します。rootユーザーは削除できません。

## IAMで権限を決める

権限はIAMポリシーで決まり、操作ごとに評価されます。rootユーザーはすべての権限を持ちます。ほかのユーザーには、本人またはグループに付けたポリシーの権限が適用されます。

テナントには最初から3つのポリシーがあります。

| ポリシー             | 許可する操作                                        |
| -------------------- | --------------------------------------------------- |
| Tenant Administrator | すべての操作                                        |
| Tenant Writer        | テナント、ユーザー、認証情報、IAMの管理を除くすべて |
| Tenant Reader        | 読み取りだけ                                        |

> `readers`というグループを作成し、Tenant Readerポリシーを付けて、aliceを追加してください。各手順は実行前に見せてください。

| 作業                         | ツール                                                                                                                                       |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| ポリシー                     | `create_iam_policy`, `get_iam_policy`, `list_iam_policies`, `update_iam_policy`, `delete_iam_policy`                                         |
| グループ                     | `create_iam_group`, `get_iam_group`, `list_iam_groups`, `update_iam_group`, `delete_iam_group`                                               |
| グループのメンバーとポリシー | `add_group_member`, `remove_group_member`, `list_iam_group_members`, `attach_group_policy`, `detach_group_policy`, `list_iam_group_policies` |
| ユーザーのポリシー           | `attach_user_policy`, `detach_user_policy`, `list_iam_user_policies`                                                                         |
| 監査記録                     | `list_iam_audit`（独立した`audit` grantが必要）                                                                                              |

ポリシーの文書には、`effect`、`actions`、`resources`を持つstatementを並べます。resourcesにはテナント、すべてのワークスペース、特定のワークスペースを指定できます。変更は次の操作から反映されます。

## 一時的なロール

ロールを使うと、一時的な認証情報を渡せます。`create_iam_role`で、引き受けてよい対象（テナント、ユーザー、グループ、サービス用キー）を示す信頼ポリシーと一緒に作成します。`attach_role_policy`でポリシーを付けたあと、許可された呼び出し元が`assume_role`を使います。セッションは900秒〜12時間（既定は1時間）で、秘密値は一度しか表示されず、ロールのポリシーだけで評価されます。rootユーザーとロールのセッションは別のロールを引き受けられません。ロールを削除すると、そのセッションも失効します。

## ワークスペースへのアクセス

テナントユーザーには、そのワークスペースを対象に含むポリシーが必要です。ワークスペースの直接の役割を追加するには、`grant_workspace_member`でそのワークスペースでの役割（Admin、Member、Viewer。コンテンツ操作の上限はそれぞれ`migration`、`write`、`read`）を指定し、取り消すには`revoke_workspace_member`を使います。`list_workspace_members`は直接付与した権限だけを一覧します。取り消すと、そのワークスペースに紐付く本人のキーも失効します。

キーのコンテンツのスコープも上限になり、実効的な権限は両方のうち狭い方です。`audit` grantは`read`、`write`、`schema`、`migration`のスコープと独立していて、ポリシーやワークスペースの役割では付与されません。

## テナントとワークスペースの管理

> 接続中のテナントとワークスペースの名前とUUIDを見せてください。変更はしないでください。

名前が同じでも別の保存先の場合があります。`whoami`でUUIDを確認してから変更を依頼してください。

| やりたいこと                               | 使うツール                                                                 | 注意点                                                                  |
| ------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| テナント名や手動のワークスペース上限を変更 | `get_tenant`, `update_tenant`                                              | プランの上限は変わらない                                                |
| ワークスペースを作成・確認・削除           | `create_workspace`, `list_workspaces`, `get_workspace`, `delete_workspace` | テナント用キーが必要。削除するとデータも失われ、最後の1つは削除できない |
| ワークスペース名やエンティティ上限を変更   | `update_workspace`                                                         | 上限の変更にはテナントの更新権限も必要                                  |
| 自分の表示名を変更                         | `get_current_user`, `update_current_user`                                  | 本人に紐付くキーが必要                                                  |

手動上限を変更するには、テナントでは`replace_max_workspaces=true`と`max_workspaces`、ワークスペースでは`replace_max_entities=true`と`max_entities`を指定します。解除する場合は値に`null`を指定します。項目の省略だけでは解除されず、プランによる上限は別に適用されます。

## 新しいワークスペースを準備する

スキーマのない新しいワークスペースでは、状態が`schema_pending`と表示されます。最初のスキーマを作成すると状態が`active`になり、そのバージョンが`schema_id`に記録されます。情報を保存する前に、アシスタントにワークスペースの詳細を確認するよう依頼してください。

ほかのワークスペースの埋め込み設定はコピーされません。個別の設定がなければ、サーバーで既定のproviderを使う場合があります。[埋め込みの設定](../../configuration/embedding/)でproviderと検索データの準備状況を確認してください。情報を保存したあとにワークスペースのproviderを設定すると、検索データが再生成されます。

## 運用者だけが行う操作

- コマンドラインでのテナント作成、サーバー全体のテナント一覧、物理削除は、サーバー運用者の作業です。[テナントの廃止](../../operations/tenant-retirement/)を参照してください。
- サーバー全体のユーザー一覧と本人アカウントの削除も運用者の作業で、テナントからの退会とは別です。
- スキーマのarchiveはデータの物理削除ではありません。共有テンプレートのライブラリも物理的なPostgreSQL schemaとは別です。[テンプレート](../templates/#スキーマのバージョンとarchive)を参照してください。
- すべてのREST操作をMCPから実行できるわけではありません。Marketplace公開、推論ジョブ、ログイン・OAuth、Stripe webhook、サーバー保守は、それぞれの手順で行います。providerの設定だけで推論が実行されたり、ライセンスの制限が解除されたりすることもありません。

`export_jsonl`は`GET /api/export.jsonl`に、`import_jsonl`と`import_job_status`は取り込み用エンドポイントに対応します。上限は[エクスポートとインポート](../import-export/)を参照してください。

アシスタントを通じて、`capabilities`でキーの権限を確認し、`recall_context`で関連情報を取得し、`get_entity_drift`で保存した情報と有効なスキーマを比較し、`discover_workspaces`でアクセス候補を確認できます。`migration_dry_run`は、現在のバージョンの件数、必須の値が足りている古いバージョンの件数、必須の値が不足する件数を数えます。変更案のプレビューは行いません。

権限を取り消しても、認証済みのリクエストは完了する場合があります。キューの処理では書き込み前に権限が再確認されますが、すでに進行中の外部呼び出しがすべて止まる保証はありません。キーの交換は[APIキー](../api-keys/)を参照してください。
