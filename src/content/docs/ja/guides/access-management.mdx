一緒に使う人を招待し、必要なワークスペースだけを共有できます。招待やテナント全体のメンバー管理は、テナントのAdminまたはOwnerに依頼してください。テナントは組織や個人の利用範囲、ワークスペースはその中で情報を分けて保存する場所です。

## 共同利用者を招待する

テナントのAdminまたはOwnerは、接続済みのAIアシスタントに次のように依頼できます。

> このメールアドレスの人をMemberとして招待したいです。宛先、役割、有効期限を確認してから招待を作成してください。

1. アシスタントが`create_invite`で作成した招待のトークンを受け取ります。Ownerとして招待できるのはOwnerだけです。
2. トークンを非公開の方法で相手に渡します。招待メールは自動送信されません。
3. 相手は招待を使って登録します。すでにアカウントがあれば、そのアカウントで認証して`accept_invite`で受諾します。保存済みのメールアドレスが招待先と一致する必要があります。サービス用のキーでは受諾できません。
4. MemberまたはViewerには、使うワークスペースの権限も付与します。テナントへの参加だけではワークスペースを使えません。

招待の受諾ではログイン用のキーは発行されず、接続中のワークスペースも切り替わりません。ログインや登録には通常の認証手順を使ってください。変更可能な未検証メールだけでは本人確認になりません。

招待の状態は`list_invites`で確認できます。未使用の招待を取り消すには`revoke_invite`、トークンを作り直すには新しい期限を指定した`reissue_invite`を使います。再発行すると古いトークンは使えなくなります。新しいトークンは自分で相手に渡してください。一覧にはトークンは表示されません。

## 役割と実効権限

保存・編集などの操作は本人の役割とAPIキーの両方で許可されている必要があります。キーだけを強い権限にしても、本人の役割で許可されていない操作はできません。

| テナントの役割 | できることの上限                                | ワークスペースへの参加             |
| -------------- | ----------------------------------------------- | ---------------------------------- |
| Owner / Admin  | `migration`までのコンテンツ操作とテナントの管理 | テナント内の管理権限を継承         |
| Member         | `write`までのコンテンツ操作                     | ワークスペースごとの権限付与が必要 |
| Viewer         | `read`までのコンテンツ操作                      | ワークスペースごとの権限付与が必要 |

ワークスペースにはAdmin、Member、Viewerを付与できます。それぞれのコンテンツ操作の上限は`migration`、`write`、`read`ですが、テナントの役割の上限も適用されます。たとえばテナントのMemberがワークスペースのAdminになっても、コンテンツの操作は`write`までです。直接のワークスペース権限は管理できますが、`schema`権限は得られません。チーム単位の権限付与には対応していません。

> このワークスペースを使える人を確認し、指定したメンバーにViewerを付与してください。変更前に対象者とワークスペースを見せてください。

ワークスペースのAdminは`list_workspace_members`、`grant_workspace_member`、`revoke_workspace_member`で個人の権限を管理できます。相手は先にテナントに参加している必要があります。一覧に出るのは直接付与した権限だけで、テナントのOwner/Adminが継承したアクセスは含みません。

ワークスペースのAdminだけでは、テナントへの招待・メンバー管理、APIキー発行、所有権移譲、課金管理はできません。直接の権限を取り消すと、継承したアクセスがない場合は対象のワークスペースに紐付くキーも失効します。テナントへの参加は取り消されません。

役割を昇格させても、すでに発行したキーのスコープは広がりません。監査記録には別途`audit` grantが必要で、管理者でも自動では付与されません。サービス用のキーには本人の役割がなく、本人としての管理操作やプロフィール変更はできません。キーのスコープ、対象範囲、期限、テナントが有効であることは引き続き必要です。

## メンバーと所有権の変更

> この人の役割を変更すると、使えなくなるワークスペースやキーを先に確認してください。まだ変更しないでください。

`preview_member_role_change`や`preview_member_removal`で影響を確認してから、変更を依頼してください。プレビューは確認した時点の情報であり、その後の操作の許可を保証しません。

既存のアカウントを追加したり役割を変えたりする場合は`list_members`と`set_member_role`を使います。アカウントがない相手には招待を送ってください。`remove_member`で参加を取り消すと、本人に紐付くテナントのキーも失効します。ただし、ほかのテナントでも使う本人のアカウントは残ります。

Ownerを追加・削除できるのはOwnerだけです。最後のOwnerは削除も降格もできません。引き継ぐときは、既存のメンバーのUUIDを確認して`transfer_ownership`を使います。所有権の移譲と同時に、呼び出した本人はAdminになります。

## テナントとワークスペースの管理

> 接続中のテナントとワークスペースの名前とUUIDを見せてください。変更はしないでください。

名前が同じでも別の保存先の場合があります。`whoami`でUUIDを確認してから管理操作を依頼してください。

| やりたいこと                               | 使うツール                                                                 | 依頼できる人と注意点                                                                            |
| ------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| テナント名や手動のワークスペース上限を変更 | `get_tenant`, `update_tenant`                                              | テナントのAdmin/Owner。プランの上限は変わらない                                                 |
| ワークスペースを作成・確認・削除           | `create_workspace`, `list_workspaces`, `get_workspace`, `delete_workspace` | 作成・削除はテナントのAdmin/Owner。削除するとデータも失われ、最後の1つは削除できない            |
| ワークスペース名を変更                     | `update_workspace`                                                         | ワークスペースのAdmin。スキーマの紐付けは変わらない                                             |
| 手動のエンティティ上限を変更               | `update_workspace`                                                         | テナントのAdmin/Ownerが必要                                                                     |
| 自分の表示名を変更                         | `get_current_user`, `update_current_user`                                  | 本人に紐付くキーが必要。変更はほかのテナントにも反映され、メール・パスワード・OAuthは変更しない |

手動上限の変更には、テナントでは`replace_max_workspaces=true`と`max_workspaces`、ワークスペースでは`replace_max_entities=true`と`max_entities`を指定します。解除する場合は値に`null`を指定します。項目の省略だけでは解除されず、プランによる上限は別に適用されます。

選択中のワークスペースの取得・変更・スキーマ操作では、キーの対象を切り替えられません。直接の権限管理とワークスペース削除では、同じテナント内の対象を明示し、操作ごとに権限が確認されます。キーの接続先を自由に切り替えられるわけではありません。

## 新しいワークスペースを準備する

`schema_id`を指定せずに作成したワークスペースは`status: "schema_pending"`で始まります。最初のスキーマを作成すると`status: "active"`になり、そのバージョンが`schema_id`に記録されます。両方の項目は`GET /api/workspaces`で確認できます。

ワークスペースを作成しても、ほかのワークスペースの埋め込みprovider設定や、記録済みのモデル・次元数はコピーされません。ワークスペース個別の設定がなければ、デプロイ全体のproviderを使う場合があります。意味による検索を使う前に、管理者に[埋め込みの設定](../../configuration/embedding/)に沿って実際に使うproviderと埋め込みの処理状況を確認してもらってください。エンティティがある状態でワークスペースのproviderを設定するとreindexが行われます。空のワークスペースには再処理する既存エンティティがありません。

## 管理操作の境界

通常の共同利用は上記のツールで管理できます。次の操作は扱いが異なります。

- テナントの作成、サーバー全体のテナント一覧、物理削除は、サーバー運用者がoperator CLIで行います。テナントのキーでは実行できません。[テナントの廃止](../../operations/tenant-retirement/)を参照してください。
- サーバー全体のユーザー一覧と本人アカウントの削除も運用者に依頼します。テナントからの退会とは別です。
- スキーマのarchiveはデータの物理削除ではありません。共有テンプレートのライブラリも物理的なPostgreSQL schemaとは別です。[テンプレート](../templates/#スキーマのバージョンとarchive)を参照してください。
- すべてのREST操作をMCPから実行できるわけではありません。Marketplace公開、推論ジョブの実行、ログイン・OAuth、Stripe webhook、サーバー保守は管理MCPの対象外です。providerの設定だけで推論が実行されたり、ライセンスの制限が解除されたりすることもありません。

情報の書き出し・取り込みには両方が対応しています。`export_jsonl`は`GET /api/export.jsonl`に、`import_jsonl`と`import_job_status`は取り込み用エンドポイントに対応します。上限は[エクスポートとインポート](../import-export/)を参照してください。招待の受諾にもRESTがあります。認証済みのアカウントでは`POST /auth/invites/accept-authenticated`、既存アカウントの認証情報を使う場合は`POST /auth/invites/accept`です。

MCPだけのツールには`capabilities`（プロトコルの機能確認）、`recall_context`（関連情報の一括取得）、`get_entity_drift`（有効なスキーマとの差分）、`discover_workspaces`（アクセス候補の確認）、`migration_dry_run`（スキーマ変更のプレビュー）があります。RESTだけの操作には`/api/schemas/active/{name}/infer-fill`、`/api/inference-jobs/*`、`/api/marketplace`とその関連操作、`/api/system/maintenance`、`POST /api/stripe/webhook`、`/auth/oauth/*`、初回セットアップがあります。

権限を取り消しても、認証済みのリクエストは完了する場合があります。キューの処理では書き込み・公開前に権限が再確認されますが、すでに進行中の外部呼び出しがすべて止まる保証はありません。キーの交換は[APIキー](../api-keys/)を参照してください。
