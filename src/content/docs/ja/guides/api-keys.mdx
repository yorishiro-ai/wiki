クライアントごとに別のキーを使い、必要な権限だけを付与してください。テナントのAdmin/OwnerはRESTまたはMCPでキーを管理できますが、発行元のスコープ、独立したaudit grant、対象範囲、有効期限を超えられません。ワークスペースのAdminだけでは発行できません。役割による上限は[アクセス管理](../access-management/)を参照してください。

## キーを発行する

`POST /api/api-keys`は`name`、任意の`scope`、`audit`、未来の`expires_at`を受け付けます。スコープの既定値は`read`、`audit`は`false`です。未対応のセキュリティ関連フィールドは拒否されます。名前は1〜100文字です。

```sh
curl -X POST http://localhost:5150/api/api-keys \
  -H 'Authorization: Bearer <api-key>' \
  -H 'Content-Type: application/json' \
  -d '{"name":"Notes assistant","scope":"write","audit":false}'
```

URLとキーのプレースホルダーを置き換えてください。発行・ローテーション時の秘密値は一度しか返されないため、`full_key`を非公開の場所に保存します。MCPでは`create_api_key`を使います。期限を設ける場合は未来のRFC 3339形式の日時を`expires_at`に指定します。発行元の期限、スコープ、audit権限、対象範囲を広げることはできません。

`write`はコンテンツを変更できますが、スキーマ管理はできません。`schema`と`migration`はより高いコンテンツのスコープで、auditとは独立しています。役割の変更により、保存された権限を変えずに実効権限が狭くなることがあります。利用者が昇格しても、既存の狭いキーの権限は広がりません。

## 権限と履歴を確認する

`GET /api/api-keys`または`list_api_keys`を使います。保存された権限と実効権限、対象範囲、本人への紐付け、`last_used_at`、各段階の日時、active/revoked/expiredの状態を確認できます。失効済み・期限切れのキーも履歴に残ります。一覧に秘密値や`key_hash`は含まれません。日時は設定されたタイムゾーンで表示されます。

`whoami`で現在のテナント・ワークスペースと実効権限、`discover_workspaces`で現在のキーのテナント内の候補、`capabilities`で現在の権限情報を確認できます。サービス用のキーで取得できる候補は選択中のワークスペースだけです。候補の取得はアクセスの許可ではありません。`scope_satisfied` / `grants_satisfied`も、役割、対象へのアクセス、ライセンスによる許可を保証しません。

ワークスペースに紐付くキーは対象を切り替えられません。Enterpriseのテナントに紐付くキーでは、アクセスを許可されたワークスペースのUUIDを`X-Workspace-Id`に指定します。表示名は使いません。このヘッダーで直接の権限やほかの認可を回避することはできません。

## ローテーションと失効

| 作業           | REST                             | MCP              |
| -------------- | -------------------------------- | ---------------- |
| ローテーション | `POST /api/api-keys/{id}/rotate` | `rotate_api_key` |
| 失効           | `DELETE /api/api-keys/{id}`      | `revoke_api_key` |

ローテーションは後継のキーを1つ作成して元のキーを失効させる処理を一括で行い、スコープ、audit、本人への紐付け、対象範囲、期限を保ちます。返された`full_key`を保存し、すぐにクライアントを更新してください。元のキーでは認証できなくなります。無効なキーはローテーションできません。同時に実行しても後継は1つだけなので、再度秘密値が返ると考えず競合を処理してください。履歴には`replaced_by_id`が記録されます。

失効は認証用ハッシュを破棄し、秘密値を含まない権限の履歴を残します。切り替え中に両方のキーを使う必要がある場合は、許可された別のキーを発行してクライアントを更新し、その後で古いキーを失効させてください。ローテーションでは両方を有効に保てません。

メンバーを削除すると本人に紐付くテナントのキーが失効します。ワークスペースの直接の権限を取り消した場合も、対象の紐付いたキーが失効します。テナントの無効化ではすべてのキーが失効し、履歴とデータは残ります。operatorによるテナントの完全削除ではキーの履歴も削除され、秘密値を含まない廃止の記録だけが残ります。[テナントの廃止](../../operations/tenant-retirement/)を参照してください。

## 監査とエラーの確認

`list_audit_log`は、独立したaudit grantがある場合だけ、選択中のワークスペースの監査記録をページ単位で取得できます。高いコンテンツのスコープや、テナント・ワークスペースの管理者の役割だけではこの権限を得られません。

MCPクライアントはHTTP 200だけで判断せず、JSON-RPCエラーとツールの戻り値の`isError`を確認してください。アクセスできない場合は、広いキーを求める前に期限、失効、実効的な役割、対象範囲、資源とライセンスの制限を確認します。ログ、画面の共有、問い合わせに秘密値を含めないでください。
