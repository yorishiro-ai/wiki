APIキーはAIアシスタントをYorishiroに接続するための秘密の値です。管理者から受け取ったキーをMCPクライアントに登録してください。キーを持つ人はその権限を使えるため、チャットや共有ログに貼らないでください。

クライアントごとに別のキーを使い、必要な権限だけを付与してください。こうすると、1つの接続だけを停止・交換できます。発行と管理はテナントのAdmin/Ownerに依頼します。ワークスペースのAdminだけでは発行できません。

## キーを発行する

管理者は接続済みのアシスタントに次のように依頼できます。

> メモの保存用に、名前がNotes assistant、スコープがwrite、監査権限なしのAPIキーを作成したいです。権限と対象のワークスペースを確認してから発行してください。

`create_api_key`で発行します。読むだけなら`read`、保存・編集には`write`、スキーマ管理には`schema`が必要です。`migration`はさらに高いコンテンツのスコープです。監査記録を読む`audit` grantはこの順序と独立しています。指定しなければ`read`、`audit=false`になります。

名前は1〜100文字です。期限が必要なら`expires_at`に未来のRFC 3339形式の日時を指定します。発行元のキーより広いスコープ、audit権限、対象範囲、長い期限にはできません。利用者の役割による制限も適用されます。

返された`full_key`は一度だけ表示されます。パスワードマネージャーなどに保存し、[MCPクライアント](../../installation/first-run/#4-mcpクライアントを接続する)に設定してください。

APIを直接使う場合は、URLと`<api-key>`を置き換えて実行します。未対応のセキュリティ関連フィールドは受け付けません。

```sh
curl -X POST http://localhost:5150/api/api-keys \
  -H 'Authorization: Bearer <api-key>' \
  -H 'Content-Type: application/json' \
  -d '{"name":"Notes assistant","scope":"write","audit":false}'
```

## 権限と履歴を確認する

> 接続中のワークスペースと、このキーでできる操作を確認してください。秘密値は表示しないでください。

`whoami`で接続先と実効権限、`capabilities`でキーの権限情報を確認できます。ただし、`scope_satisfied`や`grants_satisfied`が満たされていても、役割、対象へのアクセス、ライセンスの条件により操作できない場合があります。役割を昇格させても既存のキーのスコープは広がりません。

管理者は`list_api_keys`または`GET /api/api-keys`でキーの名前、対象範囲、本人への紐付け、保存された権限と実効権限、`last_used_at`、発行・失効などの日時を確認できます。activeは有効、revokedは失効済み、expiredは期限切れです。日時は設定されたタイムゾーンで表示されます。失効・期限切れの履歴も残りますが、秘密値や`key_hash`は取得できません。

`discover_workspaces`は現在のキーのテナント内の候補を返します。サービス用のキーでは選択中のワークスペースだけです。候補が見えてもアクセスが付与されるわけではありません。ワークスペースに紐付くキーは対象を切り替えられません。Enterpriseのテナントに紐付くキーでは、許可されたワークスペースのUUIDを`X-Workspace-Id`に指定します。名前は使えず、この指定で権限の制限は回避できません。

## ローテーションと失効

キーを交換するときは、現在の接続が止まるタイミングに注意してください。

1. `rotate_api_key`で交換すると、同じスコープ、audit、本人への紐付け、対象範囲、期限の新しいキーが1つ発行され、元のキーは同時に失効します。
2. 返された`full_key`を保存し、すぐにクライアントの設定を更新します。
3. 再接続して読み取りを試してください。

無効なキーは交換できません。同時に交換しても後継は1つだけです。競合した場合は、もう一度秘密値が返るとは考えず管理者に確認してください。履歴の`replaced_by_id`で後継を確認できます。

切り替え中も古いキーを使う必要がある場合は、別のキーを新規発行してクライアントを更新し、確認後に`revoke_api_key`で古いキーを失効させます。ローテーションでは両方を有効に保てません。失効後は認証できませんが、秘密値を含まない履歴は残ります。

| 操作 | REST                             | MCP              |
| ---- | -------------------------------- | ---------------- |
| 交換 | `POST /api/api-keys/{id}/rotate` | `rotate_api_key` |
| 失効 | `DELETE /api/api-keys/{id}`      | `revoke_api_key` |

テナントからのメンバー削除では本人のテナントのキーが、直接のワークスペース権限の取り消しでは対象のキーが失効します。テナントの無効化ではすべてのキーが失効し、データと履歴は残ります。運用者による完全削除ではキーの履歴も削除され、秘密値を含まない廃止の記録だけが残ります。[テナントの廃止](../../operations/tenant-retirement/)を参照してください。

## 監査とエラーの確認

監査記録が必要なら、管理者に独立した`audit` grantを依頼してください。`list_audit_log`で選択中のワークスペースの記録をページ単位で取得できます。管理者の役割や高いコンテンツのスコープだけでは読めません。

操作に失敗したら、期限、失効、本人の役割、キーの対象範囲、対象資源とライセンスの制限を確認します。HTTP 200でも処理が失敗している場合があるため、アシスタントにツールのエラーも確認してもらってください。クライアントの詳細表示ではJSON-RPCエラーと`isError`が手がかりになります。問い合わせにキー、パスワード、非公開の内容を含めないでください。
