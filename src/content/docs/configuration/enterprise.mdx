This page is for administrators of an Enterprise (`ee`) installation. Ordinary MCP use is the same as Community. Use the Enterprise image or package and configure a valid licence for licensed features.

## Licence

In the production configuration, set `YORISHIRO_LICENSE_KEY`, or edit `initializers.licence_key` in the configuration file. Without a valid, unexpired licence, Enterprise allows only one tenant. SQLite remains limited to one tenant even with a licence.

For packages, keep secrets in the protected `production.yaml`; you do not need an extra environment file. See [Packages](../../installation/packages/#configuration).

## OAuth2 and OIDC sign-in

Register Yorishiro with your identity provider and configure:

| Production variable             | Configuration field                |
| ------------------------------- | ---------------------------------- |
| `YORISHIRO_OAUTH_ISSUER_URL`    | `initializers.oauth.issuer_url`    |
| `YORISHIRO_OAUTH_CLIENT_ID`     | `initializers.oauth.client_id`     |
| `YORISHIRO_OAUTH_CLIENT_SECRET` | `initializers.oauth.client_secret` |
| `YORISHIRO_OAUTH_REDIRECT_URI`  | `initializers.oauth.redirect_uri`  |

Set an explicit public redirect URI ending in `/auth/oauth/callback`, and register exactly that URI with the provider. Use HTTPS except for local loopback testing. The default redirect is only for local testing and follows the configured listener; `HOST` does not configure it. MCP clients still use API keys.

## Per-workspace embedding provider

Use `PUT /api/workspace/embedding-key` to give a workspace its own service. Supply `base_url`, `model`, `api_key`, and the model's `dimensions`; use `send_dimensions_param` only if the provider expects it. Reading the settings does not return the API key.

Changing the model requires rebuilding search data. Follow [Embedding](../embedding/#change-the-embedding-model) and keep the embedding worker running.

## Worker class per workspace

`PUT /api/workspace/worker-class` selects `shared`, `official`, or `tenant_private` with the `worker_class` field. Leave it at `shared` unless you have provisioned dedicated workers.

Before choosing another class, start both kinds of worker for its target and declare the embedding route on the server. See [Worker targets](../workers-and-queues/#worker-targets). Declaring a target does not start or monitor workers.

## Asynchronous infer-fill

Infer-fill proposes missing field values with an LLM. It does not apply suggestions until you confirm them. Use this when you want reviewed suggestions rather than fixed schema defaults.

1. Set the workspace LLM credentials through `PUT /api/workspace/llm-key`.
2. Start inference with `POST /api/schemas/active/{name}/infer-fill` and save the returned `job_id`.
3. Poll `GET /api/inference-jobs/{job_id}` until `completed` or `failed`.
4. Read `GET /api/inference-jobs/{job_id}/proposals` and review the suggestions.
5. Confirm with `POST /api/inference-jobs/{job_id}/confirm`, or reject or discard with the corresponding endpoint.

Confirmation is also asynchronous: it returns a new `job_id`. Poll `GET /api/inference-jobs/confirmations/{job_id}` before treating changes as applied. Keep `job-target:shared` running for inference and confirmation. Listing needs `read` access; reviewing actions and confirmation status need `schema` access.

Review failures and stale proposals rather than assuming every suggestion was applied. Do not resubmit a job merely because it is still queued; check [Troubleshooting](../../operations/queue-start-objectives/).

## Template updates and schema forks

For a schema linked to a template, ask your assistant to use `list_upstream_changes`, then `merge_preview`. Review the preview before `merge_apply`, especially if you changed local fields. Conflicts leave the update pending. See [Built-in templates](../../guides/templates/).

`POST /api/schema-forks` copies an active schema from another workspace in the same tenant. The copy has its own history. Following its source again through `PUT /api/schema-forks/{fork_id}` can discard local changes and requires `force=true` when it would do so; review those changes first.

## Plan policy and job limits

Leave `YORISHIRO_PLAN_POLICY_ENABLED=false` unless you operate plan-based hosting. Enabling it applies plan limits to workspaces, entities, and concurrent work.

| Production variable                           | Default | Limit                                                 |
| --------------------------------------------- | ------- | ----------------------------------------------------- |
| `YORISHIRO_WORKER_CLASS_SHARED_LIMIT`         | `1`     | Concurrent shared work                                |
| `YORISHIRO_WORKER_CLASS_TENANT_PRIVATE_LIMIT` | `1`     | Concurrent private work per tenant                    |
| `YORISHIRO_WORKER_OFFICIAL_LIMIT`             | By plan | Concurrent Official work: Free `1`, Pro `4`, Team `8` |

Explicit limits must be positive. These settings do not create workers or increase the provider's capacity. In a configuration file, use `initializers.plan_policy_enabled` and `initializers.worker_admission`.

For Stripe integration, configure `YORISHIRO_STRIPE_WEBHOOK_SECRET`, `YORISHIRO_STRIPE_PRICE_PRO`, and `YORISHIRO_STRIPE_PRICE_TEAM`, or the corresponding `initializers.stripe` fields. Keep the webhook secret private.
