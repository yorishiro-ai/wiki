If you use the [Compose example](../../installation/docker-compose/) or [packages](../../installation/packages/), run all four services. You do not need dedicated worker pools for a personal installation.

## Processes

| Service          | Command                                         | Handles                                               |
| ---------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Server           | `yorishiro start`                               | API and MCP requests                                  |
| Embedding worker | `yorishiro start --worker=worker-target:shared` | Embedding updates, query embeddings, reindexing       |
| Application jobs | `yorishiro start --worker=job-target:shared`    | Imports, filling defaults, undo, Enterprise inference |
| Scheduler        | `yorishiro scheduler`                           | Recovery and scheduled tasks                          |

Keep the two worker commands in separate processes. Do not mix `worker-target:*` and `job-target:*` in one command. A bare `--worker`, `--all`, or `--server-and-worker` is not supported.

Use the same database, queue, and relevant provider settings on every service. If the database or queue uses SQLite, keep all services on one host and use absolute paths to the same files. Workers on another machine require PostgreSQL data storage and a PostgreSQL or Valkey queue.

## Worker targets

Only change these when you need separate capacity for Enterprise workspaces. A target selects which work a worker handles; it does not start a worker for you.

| Pool       | Embedding command argument                  | Application jobs argument                |
| ---------- | ------------------------------------------- | ---------------------------------------- |
| Shared     | `--worker=worker-target:shared`             | `--worker=job-target:shared`             |
| Official   | `--worker=worker-target:official`           | `--worker=job-target:official`           |
| One tenant | `--worker=worker-target:tenant:<tenant-id>` | `--worker=job-target:tenant:<tenant-id>` |

Use a lowercase, hyphenated tenant UUID, not a workspace ID. Keep shared workers running too: query embeddings and inference use shared services.

Before assigning a workspace to a dedicated pool:

1. Start the corresponding embedding and application-job workers with the same configuration as the server.
2. Add the embedding target to `settings.worker_targets` on the server, keeping `worker-target:shared`. In production, `YORISHIRO_WORKER_TARGETS` accepts a JSON array, such as `["worker-target:shared","worker-target:official"]`.
3. Restart the server with that declaration, then assign the workspace through `PUT /api/workspace/worker-class`. See [Enterprise configuration](../enterprise/#worker-class-per-workspace).

The declaration is not a health check. Monitor the processes yourself. To remove or change routing, stop new work and let the old workers finish pending work before replacing them.

One process may serve several targets of the same kind by separating them with commas. Those targets share the process's capacity; they do not each get reserved capacity.

## Worker settings

Change these only after checking [Troubleshooting](../../operations/queue-start-objectives/). Adding workers will not fix an unavailable model or database.

| Production variable                  | Default                               | Use                                              |
| ------------------------------------ | ------------------------------------- | ------------------------------------------------ |
| `YORISHIRO_QUEUE_WORKERS`            | `1` for SQLite queues, `2` otherwise  | Concurrent work in each worker process           |
| `YORISHIRO_QUEUE_REAPER_AGE_MINUTES` | `30`                                  | Recovery age for queue work left in processing   |
| `DB_MAX_CONNECTIONS`                 | `10` for SQLite, `100` for PostgreSQL | Maximum connections per configured database pool |

SQLite allows one writer at a time. Prefer PostgreSQL when concurrent writes become a problem rather than increasing SQLite worker counts. Enterprise can also [limit simultaneous work](../enterprise/#plan-policy-and-job-limits).
